QuickDash — Windows Build Setup

What a Windows machine needs to build QuickDashCustomerApp, vendorApp, and vendorWeb (all Flutter), verified against each project's actual config — not generic Flutter boilerplate. Sections 1–8 cover Customer App plus the shared Android toolchain both mobile apps need; sections 9–10 cover what's different for Vendor App and Vendor Web specifically.

2 Environment variables

  • ANDROID_HOME (or ANDROID_SDK_ROOT) → e.g. C:\Users\<you>\AppData\Local\Android\sdk
  • PATH should include:
    • %ANDROID_HOME%\platform-tools (gives you adb)
    • %ANDROID_HOME%\cmdline-tools\latest\bin
    • the Flutter SDK's own bin folder
  • JAVA_HOME → pointing at a JDK 17 install

If adb isn't recognized in a fresh shell even after adding it to PATH, use the full path directly (%ANDROID_HOME%\platform-tools\adb.exe) rather than fighting shell PATH caching.

3 Android SDK components

Install via Android Studio's SDK Manager (or sdkmanager CLI):

  • Android SDK Platform 35 — Customer App
  • Android SDK Platform 36 — Vendor App (§9); Customer App doesn't need this one
  • Android SDK Build-Tools (matching 35 and 36) — verified installed on this machine: 30.0.3, 33.0.1, 34.0.0, 37.0.0 all coexist fine, Gradle picks the version each project's build.gradle asks for
  • Android SDK Platform-Tools
  • Android SDK Command-line Tools
  • CMake 3.22.1 — not something you need to manually install; the SDK manager auto-installs it the first time a build needs it (you'll see "Installing CMake 3.22.1" scroll by), just don't be alarmed when it happens mid-build

Accept SDK licenses once: flutter doctor --android-licenses

4 Project-specific files

Good news for a fresh machine: less manual setup than you'd expect. Checked directly against git ls-files — both google-services.json files (production + staging) and the release keystore (quickdashcustomer.jks for Customer App, quickdashvendor.jks for Vendor App) are already committed to the repo, not gitignored. A plain git clone on a new machine already has them. Only android/local.properties (and, if ever added, android/key.properties) is genuinely absent — those hold machine-specific paths and aren't meant to be shared.

android/local.properties — the one file you must create yourself

sdk.dir=C:\\Users\\<you>\\AppData\\Local\\Android\\sdk
flutter.sdk=C:\\src\\flutter
flutter.buildMode=debug
flutter.versionName=1.0.3
flutter.versionCode=3
GOOGLE_MAPS_API_KEY=<your Google Maps API key>
RELEASE_STORE_FILE=../../quickdashcustomer.jks
RELEASE_STORE_PASSWORD=<keystore password>
RELEASE_KEY_ALIAS=<key alias>
RELEASE_KEY_PASSWORD=<key password>

Debug builds don't need real keystore values to run — those four RELEASE_* values only matter for a signed --release build. sdk.dir/flutter.sdk paths must match wherever you actually installed them on your machine (that's exactly why this file can't be committed — it's per-machine, not per-project). Ask whoever owns the keystore for the actual password/alias values; they aren't repeated here even though the guide is otherwise fully self-contained, since this file is version-controlled.

Firebase config (two flavors, two files) — already in the repo

  • android/app/google-services.json — production Firebase project (quick-dash-84f6a)
  • android/app/src/staging/google-services.json — staging Firebase project

Release signing keystore — already in the repo

quickdashcustomer.jks sits at the Flutter project root (referenced from local.properties as ../../quickdashcustomer.jks, two levels up from android/app/) and is already committed. Only required for a signed release build, not for debug — you still need the actual password/alias (not stored in the repo) to produce a working signed build.

5 First-time build steps

  1. flutter doctor — confirm no blocking issues
  2. flutter pub get — resolve Dart dependencies
  3. Create android/local.properties and drop in both google-services.json files as above
  4. Run a debug build for a first sanity check (see next section)

6 Build commands

This app has two flavors — production and staging — the flavor flag is required, a bare flutter run/flutter build without it will not target the flavor you expect.

# Debug APK, production flavor
flutter build apk --debug --flavor production -t lib/main.dart

# Debug APK, staging flavor
flutter build apk --debug --flavor staging -t lib/main.dart

# Release APK, production flavor (needs the real keystore values above)
flutter build apk --release --flavor production -t lib/main.dart

Output lands in build\app\outputs\flutter-apk\app-<flavor>-<mode>.apk.

7 Device testing (ADB)

  • Enable Developer Options + USB debugging on the test device
  • adb devices should list it as device (not unauthorized/offline) — accept the on-device authorization prompt if it shows unauthorized
  • Install a built APK: adb install -r build\app\outputs\flutter-apk\app-production-debug.apk
  • If the device drops to offline/unauthorized mid-session: adb kill-server && adb start-server, then re-accept the prompt

8 Known gotchas

Disk space Gradle's build cache (~/.gradle/caches) and pub cache can consume many GB. A build failing with a Jetifier/transform error mentioning "not enough space on the disk" means free up space, not a real config problem. Clearing ~/.gradle/caches is always safe (regenerates automatically) — just fully stop any Gradle daemon first (gradlew --stop) or you'll get a half-deleted, corrupted cache that breaks the next build instead.
intl version conflict pubspec.yaml's intl constraint must satisfy whatever flutter_localizations pins for your installed Flutter SDK version (Flutter 3.35.1 wants intl ^0.20.2). If flutter pub get fails with a version-solving error mentioning intl/easy_localization, bump the intl constraint in pubspec.yaml to match.
razorpay_flutter compile error on newer Flutter engines Versions before 1.4.0 use the removed Flutter v1 plugin-embedding API (PluginRegistry.Registrar) and fail with cannot find symbol: class Registrar on current Flutter engines. Project pins ^1.4.5 — don't downgrade below 1.4.0.
A successful build looks like this A handful of harmless google_api_headers "default plugin" warnings are expected and safe to ignore — the actual signal is √ Built build\app\outputs\flutter-apk\app-<flavor>-<mode>.apk at the end.

9 Vendor App (what's different)

Same overall shape as Customer App — Android with staging/production flavors, FVM-pinned Flutter, a keystore in the repo root. Everything in §1–§8 above applies except where noted below.

Project root on this PC: D:\vendorApp — NOT the copy under Downloads\QuickdashMergeApps. Both are real git clones of the same repo (Rainfont1406/quickdashStoreApp-may26), and this is exactly the kind of "which clone is actually current" trap already documented for the Admin Panel repo — the folder name/location tells you nothing. Verified directly: D:\vendorApp is 0 0 against origin/main (fully current) and has today's real build output; C:\Users\<you>\Downloads\QuickdashMergeApps\vendorApp is 5 commits behind origin (no unique unpushed work — just stale, safe to ignore, but don't build from it). Before building or editing on a machine you haven't touched in a while, always re-verify with git fetch origin main && git rev-list --left-right --count origin/main...HEAD in whichever clone you're about to use — whichever shows 0 0 is current.
Flutter version: 3.35.1, same as Customer App — as of 2026-08-23. Earlier guidance to pin this app to 3.27.3 was wrong; corrected below. Unlike Vendor Web, this app has no razorpay_flutter dependency at all (checked directly - not in pubspec.yaml), so there was never a real reason to keep it on the older engine. FVM is still fine to use if you want it (.fvmrc now says 3.35.1), but it's no longer required just to dodge a compile error the way Vendor Web genuinely does.
Real bug hit and fixed 2026-08-23: a stray dependency_overrides: intl: ^0.20.0 broke the build outright on the old 3.27.3 pin. That override (added in an unrelated commit, for reasons unclear) resolves to whatever the newest 0.20.x intl release is at pub get time - it had drifted to 0.20.3, a release requiring a newer Dart language version than Flutter 3.27.3's bundled Dart 3.6.1 supports. The build failed with Error: The specified language version is too high. The highest supported language version is 3.6., repeated across every intl source file. Switching to Flutter 3.35.1 (Dart 3.9.0) resolves it cleanly - verified live, real APK built and installed on a device. If this app ever gets pinned back to an older Flutter for some other reason, drop the intl override entirely (or pin it to a specific old version) rather than leaving an open-ended ^0.20.0 range that can drift forward on its own.

If your Flutter project and pub-cache live on different drive letters, disable Kotlin's incremental compiler. Already handled in this repo's android/gradle.properties (kotlin.incremental=false, with a comment explaining why) — on this machine the project is on D:\ and the pub cache is on C:\, and Kotlin's incremental compiler crashes with "this and base files have different roots" when computing relative paths across drives. If you ever see that exact error on a fresh machine, check this setting hasn't been accidentally reverted — the cost of disabling it is a slower full Kotlin recompile each time, not a functional problem.

Install on device (ADB)

Same as §7. One extra gotcha specific to re-installing over an existing copy: if adb install fails with INSTALL_FAILED_UPDATE_INCOMPATIBLE, the device has a differently-signed build of the same app ID already installed (common after switching keystores or pulling someone else's build) — adb uninstall com.quickdash.vendor (or .staging) first, then install fresh.

10 Vendor Web (what's different)

Project root: vendorWeb (on this PC it lives on a separate drive, D:\vendorWeb — don't assume it's a sibling of the other three apps). This is the one QuickDash project with no Android/iOS build at all in normal use — it's Flutter Web only, deployed as static files.

Much lighter setup than the mobile apps. No Android SDK, no JDK, no keystore, no local.properties, no google-services.json hunting — lib/firebase_options.dart and lib/firebase_options_staging.dart are both already committed to the repo (verified via git ls-files). The only extra thing a fresh machine needs is Google Chrome installed, for local dev (flutter run -d chrome) and for the Vendor Web build to run at all in the browser once deployed.
Pin to Flutter 3.27.3 via FVM — this is the one app that still genuinely needs it. vendorWeb/pubspec.yaml depends on razorpay_flutter ^1.2.9 (used for the web Razorpay checkout), which still uses the removed Flutter v1 plugin-embedding API and only compiles on this older engine — same reasoning that used to (incorrectly) apply to Vendor App too, see §9's correction. Don't build this against 3.35.1.

No Android flavors — use --dart-define=ENV= instead

There's no staging/production flavor split here; the same single build target picks its Firebase project (and API base URLs) at compile time from a ENV dart-define, defaulting to production if omitted:

cd D:\vendorWeb
fvm flutter pub get

# Run locally in Chrome, pointed at staging Firebase
fvm flutter run -d chrome --dart-define=ENV=staging

# Run locally in Chrome, pointed at production Firebase
fvm flutter run -d chrome --dart-define=ENV=production

Build for web

fvm flutter build web --dart-define=ENV=staging --release
fvm flutter build web --dart-define=ENV=production --release
# Output either way: D:\vendorWeb\build\web\

# Add --source-maps when you need a real stack trace to debug a
# production issue (production ships with no usable source map by
# default) - safe to deploy temporarily since it's the same code, just
# built with mappings; swap back to a plain --release build once done.
fvm flutter build web --dart-define=ENV=production --release --source-maps

Deploy — verified working method (tar + scp + ssh, not a plain scp -r)

A direct scp -r build\web\* onto the live directory works but has no backup and can leave stale files behind from a previous build (deleted assets, renamed chunks). The tested, safer sequence — run from PowerShell/Git Bash on Windows, targeting the VPS at 193.203.162.217:

# 1. Build (staging shown; swap ENV=production + the production path below for prod)
fvm flutter build web --dart-define=ENV=staging --release

# 2. Tarball the build output (avoids Windows path/wildcard issues with scp -r)
tar -czf vendorweb-build.tar.gz -C build/web .

# 3. Upload the tarball
scp vendorweb-build.tar.gz ashok@193.203.162.217:/home/ashok/vendorweb-build.tar.gz

# 4. On the server: back up the live dir, extract into a fresh incoming dir, then swap
ssh ashok@193.203.162.217 "cp -r /home/ashok/quickdash-staging-vendor-web /home/ashok/quickdash-staging-vendor-web-backup-$(date +%Y%m%d-%H%M%S)"
ssh ashok@193.203.162.217 "mkdir -p /home/ashok/vendorweb-incoming && tar -xzf /home/ashok/vendorweb-build.tar.gz -C /home/ashok/vendorweb-incoming"
ssh ashok@193.203.162.217 "rm -rf /home/ashok/quickdash-staging-vendor-web/* && cp -r /home/ashok/vendorweb-incoming/. /home/ashok/quickdash-staging-vendor-web/ && rm -rf /home/ashok/vendorweb-incoming /home/ashok/vendorweb-build.tar.gz"
# Result: https://staging-vendor.quickdash.co.in

# Production target is /home/ashok/quickdash-vendor-web/ →
# https://vendor.quickdash.co.in — same steps, different directory name,
# and double-check you built with ENV=production first.

Deploy — Firebase Hosting

# Staging
fvm flutter build web --dart-define=ENV=staging --release
firebase deploy --only hosting --project quickdash-staging
# Result: https://quickdash-staging.web.app
A second, separate PRODUCTION Firebase Hosting target exists and is live — verified: https://quick-dash-84f6a.web.app (HTTP 200, real content). .firebaserc's "default" project is quick-dash-84f6a (production), not staging. That means running firebase deploy --only hosting without an explicit --project flag deploys to this production site — separate from, and easy to confuse with, the actual customer-facing https://vendor.quickdash.co.in (served by nginx off the VPS, see the tar+scp+ssh steps above). This Firebase Hosting URL isn't the one anyone actually uses day to day, but it's real and reachable, so an accidental bare firebase deploy --only hosting here silently updates it. Always pass --project explicitly — never rely on the default.

Windows-specific gotcha: fvm not found in Git Bash

fvm: command not found in a Git Bash / bash-based shell, even though it works fine in PowerShell. dart pub global activate fvm installs a .bat shim that some bash-based shells on Windows don't pick up from PATH the same way PowerShell does. If a bare fvm fails, call the shim directly by its full path instead of fighting PATH config: "/c/Users/<you>/AppData/Local/Pub/Cache/bin/fvm.bat" flutter build web --dart-define=ENV=staging --release. PowerShell doesn't have this problem — plain fvm works there once it's on PATH.
